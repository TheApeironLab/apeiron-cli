# 通用升级、备份与恢复：方案与实现计划

状态：**草案（设计阶段，无功能代码改动）**。本文件定义待实现契约，不代表升级、备份或恢复已经可用。实现须分阶段立项，在开发前冻结支持范围和验收矩阵。

## 1. 问题与现有能力

向导支持首装及同一次安装中断后的续装，缺少受控升级入口。旧 v7 等不可识别部署仍不自动接管；本计划不能解决所有存量现场的升级，发布时必须写明从哪一版首装开始支持。

可复用 Helmfile 唯一 release 清单、依赖排序、values 解析、chartPins/imagePins、nexus-first 制品校验与导入，以及 resume 的文件校验、进程检查和私有文件写入。以下能力仍须新增，不能当作已有保障：

- 当前 `resume.rs` 绑定配置、文件摘要、集群 UID 和 CLI 二进制摘要，检查点为 `bootstrap-complete`；成功后归档到 `completed-checkpoint.json`。它不是可直接跨版本复用的升级任务，也没有逐 release 完成日志。
- 当前 `cluster::helm_state` 遇到 pending Helm 操作会拒绝继续。Helmfile postsync 失败时 release 可能已是 deployed，release 状态不能代表全部初始化或迁移成功。
- 现有 nexus-first 在 import 前会用本地 Chart 对 Nexus 执行 `sync --include-needs`，可能先修改基础组件；不能直接把首装全流程当作安全升级流程重放。
- 本 PR 基线没有方案所需的统一安装记录 API 或集群安装身份标记；两者及其首装写入路径都是新增工作。
- chentu 已有组件 `backup.sh`、`secrets export/restore` 和部分恢复验收；这不等于全平台备份与恢复已验证。CA 私钥不在常规 Secret 导出中，部分组件脚本会输出无数据或未覆盖告警。

跨仓库参考：apeiron-cli 基线 `bc31924`；评审时核对 chentu 提交 `76e08f8` 的 `deploy/helmfile/scripts/nexus_first.py`、`docs/stack/05-data-backup.md`、`specs/backup-restore/spec.md` 及组件 RUNBOOK。实现 PR 必须重新固定两仓提交，差异以能力规格和已验证行为为准，不能用陈旧总表推断已支持。

## 2. 第一版范围与不变量

1. 通用规划模型支持不同来源版本、拓扑和组件选择；首版执行器只开放可信安装记录上的**同拓扑、同架构、同组件集合**应用升级。该限制针对每个集群一次操作的前后状态，不要求不同集群具有相同版本、拓扑或组件。保留域名、入口、存储类、卷容量、节点调度和操作员配置。节点扩容、拓扑迁移、组件增删、缩容与凭据轮换须有独立执行能力及验收，未支持时明确阻断相应阶段。
2. Helmfile 仍是唯一应用部署入口；不增加第二套 release 排序、values 合并或 Chart 安装循环。升级计划读取 Helmfile 解析结果，显式迁移旧配置，遇到无法解释的漂移则拒绝。
3. 升级不删除或重置业务数据，不隐式轮换凭据。已声明并通过验收的应用迁移可以修改数据，不能承诺“数据完全不动”。
4. 第一版固定 K3s、容器运行时、存储系统、Nexus、CA 与基础网络的版本和有效配置。若目标要求变更这些组件，或 Helmfile 依赖闭包会修改它们，则拒绝该升级，不能跳过依赖强行继续。CRD/schema 变更需要单独迁移与恢复验收。
5. 所有业务升级前必须有满足本次恢复要求的备份集；checkpoint 只记录任务身份和进度，不能替代数据备份。
6. 不自动回滚、不自动恢复数据、不自动重试变更命令；允许有界只读重试。用户续升与数据恢复是独立操作，服务停机和写入冻结必须提前展示。
7. 新功能按已验收的拓扑与跨度开放。现有首装支持保留；未验证的升级目标明确显示不可用。整集群灾备、任意旧集群接管、定时备份和自动清理不在首版范围。

## 3. 安装身份、兼容关系与升级计划

### 3.1 发布包与现场解耦

**打包不得要求输入或连接已部署集群。** 发布包、现场安装记录和单次执行计划是三个分别持久化、分别校验的对象：

| 阶段/对象 | 输入 | 内容与边界 |
|---|---|---|
| 构建与发布：目标发布清单 | 固定源码、组件定义、制品、支持模式、迁移规则及发布验收证据 | 包含组件目录、镜像/Chart/工具摘要、默认配置及 schema、依赖/兼容约束、支持的来源规则和迁移/备份/恢复能力；不含实际集群身份、节点、已选组件、凭据、数据规模或备份落点 |
| 现场识别：安装记录 | 首装记录或已验收的旧记录迁移、现场只读核验 | 描述一个集群实际安装了什么、运行什么版本及配置、使用哪些数据服务和拓扑；持续记录 generation 与漂移 |
| 现场规划：本次变更计划 | 目标发布清单 + 当前安装记录及实际状态 + 操作员变更意图 | 计算实际制品闭包、组件/配置差异、操作阶段、备份范围、容量/停机、恢复路径及验收条件；绑定具体集群和基线 |

同一发布包可用于它已声明支持的不同集群。允许按架构、产品版本、部署能力或离线交付需求制作不同包，但构建过程不依赖具体集群信息。发布验收使用测试环境和能力矩阵，不把生产现场配置作为打包输入。现场可以从发布目录选择并准备所需制品，该动作是部署准备，不能反向要求重构一个集群专用发布包。

包内默认配置只用于首装或明确允许的新增字段迁移；升级必须继承现场有效配置并应用显式变更，不能用目标默认值重置组件选择、域名、凭据或存储。管理机可用公网不代表目标集群可用公网；现场计划分别检查内外网入口、代理、信任、外部依赖及离线制品闭包。

### 3.2 可信安装记录

新增有版本的安装记录，至少包含 installationId、集群 UID、generation、来源发行版本及 manifest SHA-256、拓扑/架构、节点与角色、组件选择、有效配置摘要、凭据身份引用及成功验收结果。每个组件另记录镜像/Chart 摘要、配置版本、数据库迁移状态、数据归属和依赖引用。发行版本用于追溯，不能代替逐组件的实际版本与状态。敏感配置不放入公开标记。

新首装成功后将记录持久化到私有本地状态及集群专用对象；两者须能交叉核对。旧版本仅在已定义并通过验收的记录迁移规则下升级格式；不能通过“集群里有宸途 Pod”推断归属。本地记录缺失、标记冲突、集群 UID 不符或不可解释漂移时拒绝自动升级，给出诊断导出与人工处理指引。

旧现场基线补全是只读识别与有证据的记录迁移流程，须保留原始记录及来源，不能删除原 checkpoint 或放宽首装 resume 来接管。来源镜像包含交付时本地补丁、部署名称与源码仓库改名不一致、安装后手工修改等情况均须解释。组件状态明确区分已安装、明确未安装和未知；未知不能当作未安装后重新初始化。

探测区分 `recognized`、`upgradeAvailable`、`upgradeInProgress`、`blocked`，附具体原因。识别成功不等于可升级；活动任务、健康状况、目标兼容关系和备份前提均参与判断。

### 3.3 通用引擎、组件契约与版本迁移规则

- 通用引擎负责识别、差异计算、依赖检查、计划冻结、锁与 fencing、备份门禁、阶段日志、续升对账和最终验收；不内置每次发布的专用脚本流程。
- 组件适配器声明稳定组件标识、版本识别、数据与消费者、冻结/解冻、备份/恢复方法、格式和粒度、健康及业务验证。未更新的共享服务也可能进入备份范围，因为消费者的迁移会修改其数据。适配器不能另建 Helm 安装排序或 values 合并逻辑。
- 版本迁移规则描述特定来源/目标区间的配置与 schema 变化、前置版本、必要中间步骤、写入者排空要求、可重放条件和失败处理。区分配置/程序回退、数据恢复和向前修复，不能统一承诺回滚。

每次操作由这些通用契约生成具体计划，不要求每次升级重新手写整套备份恢复方案。有新数据类型或特殊迁移的版本必须补充规则和验收；仅声明通用能力不代表支持任意组件、拓扑或版本组合。

### 3.4 显式兼容关系

保留 `release-manifest.json` 的 `upgradableFrom` 概念，但条目须为受 schema 校验的关系记录，绑定受支持来源发行清单及其摘要，或明确的逐组件来源制品/状态约束，并声明允许的拓扑/架构/组件范围、迁移策略、恢复策略与验收证据引用。两类匹配均须核验现场真实状态，不能只用发行版本字符串作授权，也不能将组件版本范围解释成任意混合状态都兼容。

publisher 从冻结的发布资料与 delivery-index 生成**候选**来源规则，不访问已部署集群；只有对应跨度、目标和组件组合通过升级与恢复验收，才能生成发布允许列表。规则可表达经验证的可选组件范围和组合约束，不能因每个组件单独通过就推断组合通过。不得从“上一版本”自动推断兼容，缺字段或缺匹配项时默认拒绝。来源可以有多个，但每条都须有证据。工具链、备份格式与安装记录 schema 的兼容性也须声明。

需要中间版本时，现场规划展示完整路径、各阶段制品与恢复点；直接跨度未受支持就拒绝直接升级。阶段间重新开放写入后，下阶段须生成新鲜恢复点，不能沿用最初备份宣称无数据丢失。组件依赖约束和部署排序仍以 Helmfile 解析结果为基础，版本迁移规则仅增加前置条件和数据操作，不形成平行部署引擎。

### 3.5 按现场组件选择计算目标

| 现场与目标情况 | 规划行为 |
|---|---|
| 已安装且目标版本或有效配置改变 | 计算升级、依赖、数据迁移及保护范围 |
| 已安装且无变化 | 保留；仍检查兼容性、hooks 和是否参与一致性备份 |
| 明确未安装，而包内包含 | 默认不安装，包内组件目录不等于现场选择 |
| 目标引入必要的新依赖 | 显式列为新增组件及数据/配置变更；首版不支持组件增删时阻断，不能隐式安装 |
| 已安装，而目标目录不再提供 | 要求有依据的保留兼容、替代或退役策略；没有策略则阻断，不能自动删除 |
| 明确要求增加或删除组件 | 独立能力、计划与验收；删除须说明数据保留/退役及消费者影响 |
| 状态未知或存在无法解释的漂移 | 阻断并补全基线，不能自动重装或覆盖 |

### 3.6 先生成只读计划，再执行意图

向导提供只读升级计划，展示来源/目标、配置与 release 差异、基础组件保持不变的检查结果、迁移影响、预计停机、备份范围/容量/落点和恢复限制。目标制品闭包必须可离线取得并校验；缺少恢复所需的旧制品也须拒绝。

部署 API 显式携带 `intent: "upgrade"`、installationId 和冻结计划摘要。后端重新校验计划，不能只依赖 UI 按钮。执行前获取以集群 UID + installationId 为键的排他锁；集群 Lease 与本地进程锁配合，覆盖不同配置路径及管理机。独立备份和恢复也使用同一排他协议。锁须有 owner、续租和 fencing 约束，无法确认旧命令停止时不接管；失去锁时停止发起新变更并进入待核查状态。

### 3.7 独立集群与复合变更

每个集群独立生成 planId、upgradeId、锁、状态目录、备份命名空间和安装 generation；以明确集群身份选择 kubeconfig/context，不能依赖管理机当前 context 或只用发布版本命名状态。复用同一包不共享可变执行状态；一个集群失败不能触发另一个集群的回退。若另有跨集群共享服务或复制，必须重新计算一致性与消费者范围，不能套用完全独立的假设。

当前需求是两个版本、拓扑及可能不同组件选择的独立集群：

| 集群 | 已知条件 | 现场计划 |
|---|---|---|
| 内网 | multi-k3s，现有 3 server，拟新增 5 agent | 核验来源记录、实际组件和数据 → 扩容前保护 → 独立扩容阶段及验收 → 提交新基线 → 应用升级前一致性备份 → 升级及业务验收 |
| 外网 | single-k3s，版本与内网不同，组件选择独立 | 核验自己的来源与目标路径 → 自己的备份/停机计划 → 升级及业务验收；不继承内网的扩容或组件选择 |

历史包 `20261016.1` 是已提供的来源线索，不能据此推断两边的当前运行版本；现场规划须分别核验，目标也不强制相同。外网验收不能替代内网断网制品、信任及恢复工具验证；源码仓库的外网部署 overlay 不能直接覆盖现场拓扑。

扩容属于独立集群变更能力，不直接复用首装全量 bootstrap。应固定现有 K3s 版本及关键配置，逐节点校验注册表/CA、网络/DNS、存储访问与实际业务负载，并在放开业务调度前验证准入隔离；加入 agent 不扩展 server/etcd 成员。新增节点不自动迁移已有卷，也不自动使 local-path 或 RWO 数据具备跨节点可用性，须核验实际 PV/PVC 和工作台访问方式。扩容执行器尚未验收时，该阶段显示不支持；若按独立已验收流程完成，须重新核验并形成升级基线，不能静默跳过。

复合变更记录父变更标识及各阶段前后 generation、成功条件和恢复边界。扩容成功而后续应用升级失败，默认保留已验收节点，按应用恢复计划处理；不能自动恢复扩容前的整个 datastore。下一阶段只在前一阶段完成、基线更新并复检后启动。single-k3s 与 multi-k3s 分别计算停机和调度策略，不因多节点就承诺滚动无中断。

## 4. 分层备份与升级前置条件

完整备份契约见 [分层备份与恢复方案](backup-recovery-design.md)。它按应用升级、基础服务升级、存储迁移、集群变更分别定义保护范围和恢复方法；该模型不扩大本方案首版的应用升级支持范围。

向导提供独立备份入口；升级复用相同适配器、排他锁和备份集，不遍历脚本后仅凭退出码放行。升级必须满足：

1. 计划列出本次操作的数据与恢复依赖，涵盖实际数据库、对象/文件、Git、专属卷、身份/密钥和配置；共享数据去重，明确排除项及可验证的重建依据。现有 Git PVC、SeaweedFS、CA 等缺口不能当作已支持。
2. 设定数据丢失窗口（RPO）、恢复时限（RTO）、停机预算和资源需求。共享服务按恢复粒度保护；恢复一个应用不得直接覆盖同实例的其他应用。
3. 冻结全部相关写入者与后台任务，形成一致恢复点；一旦重新开放写入，旧备份不能直接作为随后迁移的零丢失恢复点。
4. 备份加密且有独立于本次修改范围的副本，并从最终落点实际取回、校验、解密。取回凭据、私钥和恢复工具不能只存在于待恢复系统。密文、摘要和来源清单的可信性分别校验。
5. 区分“已生成 / 完整性已校验 / 隔离恢复已验证 / 灾备恢复已验证”。所有升级须完成本次完整性校验，每个发布跨度须有隔离恢复证据；不可逆迁移的关键数据还须用本次备份实做恢复。未验收故障域不承诺灾备。
6. 本次保护范围、backupId/清单摘要和恢复策略绑定 upgradeId；任一缺口阻断执行。备份失败前未开始业务变更，按持久记录安全解冻，不允许“忽略备份继续”。
7. 保留恢复集及匹配的旧密钥/制品，容量包含取回暂存、解密、隔离恢复和新旧卷共存。首版不自动清理或调度，恢复集在被引用期间不得删除。

## 5. 升级任务与 checkpoint

新增 `upgrade` 类型及有版本的 schema，复用 resume 的安全写入/文件校验等基础函数，不放宽原首装 resume 校验。每个 upgradeId 冻结：

- 来源安装记录摘要、集群 UID、来源 manifest 摘要和有效配置身份；
- 来源 generation、逐组件版本/schema/数据依赖及实际拓扑；有父变更时记录所属阶段；
- 目标 manifest 摘要、按现场选择解析的完整制品闭包、组件集合、目标配置及计划摘要；
- CLI/执行器摘要、备份集引用、恢复策略、锁 owner 和阶段执行记录。

旧安装身份用于授权升级；目标身份用于授权本次任务的所有续升。开始后不再重新解析“最新版本”。替换 B 包为 C 包、改变组件/配置、CLI 或执行器时拒绝续升；执行器热修复兼容迁移不在首版范围，不能通过删除 checkpoint 绕过。

本地私有持久记录与集群任务记录使用同一 upgradeId。开始升级前在锁内重新校验来源、release revision、健康、备份及目标，防止计划生成后发生漂移。执行后来源记录保持为最后完整成功版本，同时暴露任务目标及实际混合状态。

升级成功须通过应用健康、凭据可用性、数据保留/迁移和访问链路验证。提交安装身份时采用可重入协议：先将集群记录以来源 generation 校验更新为目标，再持久化本地记录与完成回执。任一步崩溃可按 upgradeId 对账完成，不能重新执行已提交任务或把半升级标成成功；冲突进入待人工处理。

## 6. 执行与失败恢复

### 6.1 执行边界

顺序为：只读计划与制品准备 → 排他锁及复检 → 一致性备份及门禁 → import → promote → Helmfile sync → 业务验证 → 提交安装记录。

- 备份前只允许计划读取与管理机本地资源准备；备份/冻结本身的写入单独记录。业务升级写入只能在备份门禁后开始。
- 复用 nexus-first 的 import/promote/sync 能力，但增加受控升级分支：检查已有 Nexus 健康与身份，不能先重放首装 `sync --include-needs` 或主机初始化。不可变导入仍逐项真实读取校验；同名不同摘要必须拒绝。
- 目标 Helmfile 解析出的依赖闭包和配置差异须符合第 2 节冻结范围；基础组件即使无版本变化，也须验证 hooks 不会造成未声明副作用。无法通过共享入口实现时，缩小支持跨度，不另建排序器。
- sync 使用原 Helmfile 依赖图；续升重新核对实际状态后协调同一目标，不承诺“从第一个未完成 release 继续”。迁移和 hook 必须有已验证的幂等性或专门恢复步骤，不能仅凭 Helm 状态跳过。

### 6.2 状态与恢复动作

| 状态 | 后续动作 |
|---|---|
| 升级尚未开始、备份失败/取消 | 不执行 import/promote/sync；按持久记录安全解除写入冻结并恢复业务，展示部分备份及失败原因 |
| `running` | 持有锁并执行阶段；拒绝并发升级、恢复和影响一致性的管理操作 |
| `failed-resumable` | 证明旧命令退出、锁有效、同一目标、备份和真实集群状态可重放后，由用户显式续升 |
| `needs-attention` | pending Helm、未知子进程、锁丢失、迁移失败或不可解释漂移；停止新变更，展示 release/阶段及固定版本 RUNBOOK |
| `completed` | 全部验证及安装身份提交完成；归档任务和备份引用 |

六阶段进度条可继续用于显示，但后端任务状态必须表达以上分支。失败后的业务是否保持只读由迁移策略决定并展示；不能自动开放写入破坏恢复点，也不能把“暂停”解释为旧版本仍可服务。

不把 `helm rollback` 或旧 bundle 重放 sync 称为数据恢复。pending 状态不自动清锁、不直接修改 Helm Secret；按该跨度已验收的操作指引处理后重新核查。诊断快照记录 release revision、Chart、values 及阶段，但不能代表跨服务事务。

### 6.3 独立恢复操作

具体恢复协议及层次边界见 [备份方案第 5 节](backup-recovery-design.md#5-恢复协议与验证等级)：共享服务恢复粒度、离线应急访问、隔离禁外发、新旧实例防双写、新集群身份映射、旧任务 fencing、会话/令牌撤销与外部副作用补偿均须纳入验收。

备份详情提供恢复计划和固定版本操作手册：选择 backupId → 检查解密身份、覆盖、目标版本和隔离落点 → 只读恢复预检/演练 → 展示停机与数据丢失窗口 → 操作员单独发起恢复。不能由升级失败自动触发。

第一版只集成通过验收的隔离恢复/验证适配器，生产原地恢复由明确 RUNBOOK 执行；UI 如实标为人工操作，不显示尚未实现的“一键恢复”。恢复到生产会覆盖选定恢复点之后的写入，执行前须重新锁定集群、确认目标和冻结写入，并保留失败现场。带 `--clean` 的 SQL 不回放到运行中的源库。

恢复顺序由组件契约给出：先建立必需的离线工具与访问/解密能力，恢复依赖的数据服务与原身份，再按依赖恢复应用并验证业务。CA、Secret、Keycloak 身份、数据库与对象必须匹配同一恢复集；不能生成新身份冒充恢复。若涉及整集群重建，按另行验收的灾备方案处理，不把首版应用恢复扩展成集群接管。

## 7. 分阶段实施与验收

| 阶段 | 交付范围 | 主要位置 | 验收 |
|---|---|---|---|
| 1. 契约与安装记录 | 分离包内发布清单、现场安装记录与执行计划 schema；固化逐组件身份、兼容/迁移与备份能力；首装写入身份 | runtime `app/resume.rs`、`app/deploy.rs`、`app/discovery.rs`；新增安装记录模块；chentu manifest、specs/RUNBOOK | 无生产集群信息可打包；schema 兼容、记录归档/迁移、未知安装拒绝、证据缺失不发布 |
| 2. 只读计划与备份 | 按现场选择解析目标、差异/冻结范围检查；复合阶段及不支持能力诊断；备份入口、适配器、独立副本、取回/解密验证和隔离恢复 | runtime `app/wizard.rs`、新增计划/备份模块；chentu 组件适配器与 BAK 规格 | 同包不同版本/拓扑/组件生成独立计划；备份真实恢复、覆盖缺口阻断、源数据不变；本阶段不开放升级执行 |
| 3. 意图与任务 | upgrade checkpoint、集群锁/fencing、冻结/解冻、备份门禁、安装记录提交对账 | runtime `app/deploy.rs`、`app/resume.rs`、新增任务模块 | 换包/换执行器拒绝、并发互斥、各持久化边界崩溃后可对账 |
| 4. 受控执行与恢复 | 复用 nexus-first 和 Helmfile；受控续升与人工恢复指引 | chentu `deploy/helmfile/scripts/nexus_first.py`；runtime `app/bootstrap.rs`、`app/cluster.rs` | 老包首装→备份→升级；故障注入→续升/隔离恢复；凭据与业务数据比对 |
| 5. 发布验收与文档 | 离线独立批次、支持矩阵、CLI/UI 指引、发布证据 | docs、能力规格、验收 harness scenario、publisher | 固定两仓源码/制品摘要，逐声明跨度及拓扑断网验收后开放入口 |

阶段串行交付，每个阶段独立 PR；阶段完成不等于功能可发布。首个支持版本必须先建立可信首装记录和可验证备份能力，不能等目标升级包到场时才要求源端具备不存在的元数据。

节点扩容能力另行交付并验收后才能接入复合变更；以上五阶段本身不承诺实现扩容、组件增删、K3s 或存储迁移。各能力独立记录支持范围，规划器可以识别操作但必须拒绝执行尚未支持的步骤。

最低验收矩阵：

| 场景 | 通过标准 |
|---|---|
| 打包与现场解耦 | 构建过程不读取生产 kubeconfig、安装记录、节点或凭据；相同发布输入产物可在不同受支持现场复用，现场信息只进入安装记录和计划 |
| 不同集群与组件选择 | 同包用于不同来源版本的 single-k3s / multi-k3s，按各自组件选择生成计划；包内未选组件不自动安装；不匹配版本/缺失组件策略明确阻断 |
| 组件与迁移兼容 | 未变更的共享服务纳入必要备份；组件各自兼容但组合不受支持时拒绝；要求中间版本时禁止直接升级；新必需依赖不得隐式安装 |
| 扩容与阶段边界 | 扩容能力未开放时明确阻断；开放后验证 3 server 加 5 agent 的初始调度隔离、镜像/网络/存储/工作台和新基线；应用失败不自动撤销已验收扩容 |
| 集群与备份隔离 | 错 context、跨集群计划/备份误用被拒绝；两个独立集群的锁、状态与恢复互不串用；迁往新集群必须走显式映射协议 |
| 正常升级与自定义配置 | 老包首装→写入业务标记→备份→新包升级；保留旧配置/凭据，验证角色授权、身份关联及对象引用；新安装记录仅在最终验证后提交 |
| 各升级拓扑 | single-k3d、single-k3s、multi-k3s 分别声明、验收；Ubuntu 22.04 AMD64 断网结果不能用本地 ARM/k3d 代替 |
| 备份失败 | 缺 age/密钥、磁盘不足、上传截断、最终落点不可读、摘要不符、解密失败或覆盖缺口均阻断升级，freeze/thaw 可恢复 |
| 备份独立性与恢复 | 关闭源应用/模拟原备份服务不可用，仍可从独立副本离线取回；用实际备份在隔离目标恢复并比对，源环境与外部系统不受影响 |
| 一致性与新鲜度 | 并发写入者被正确冻结；备份后开放写入会使原升级恢复点失效，不能沿用过期备份进入迁移 |
| 中断续升 | 在备份、import、promote、sync、验证及提交边界终止进程；重启后同一目标对账，未完成备份不标成功，旧命令未退出不接管 |
| Helm 与迁移失败 | pending-upgrade、postsync 失败但 release deployed、不可逆迁移中断均进入准确状态，按已验证步骤处理，不盲目跳过或自动回滚 |
| 身份与并发 | 改 bundle/CLI/组件/配置、替换集群、不同管理机或路径并发操作均受契约限制；失去锁后不发起新变更 |
| 基础组件边界 | 目标要求更新 Nexus/K3s/存储/CA 或依赖 hooks 有额外副作用时，在业务升级前拒绝 |
| 独立备份与恢复边界 | 无需升级即可备份/导出；显示排除项和等级；错误密钥/恢复目标被拒绝，生产恢复不由失败自动触发 |
| 恢复隔离与依赖 | 按备份方案验证共享 PG 恢复不覆盖其他应用、源 S3/API/身份失效时独立取回、演练禁外发、恢复后无旧任务双写及重复副作用；记录实际 RPO/RTO |

## 8. 发布记录与未决事项

发布记录必须包含两仓源码提交、包与 manifest 摘要、首装及升级支持范围、明确来源跨度、迁移/恢复策略、备份工具与格式、实际升级/恢复/断网证据和已知限制。候选上传不代表通过验收，只有证据完整才能更新推荐版本。

以下事项须在对应阶段开发前固定，不能作为宽松默认值进入生产：发布清单、安装记录及计划对象/API 的最终 schema；稳定组件标识与版本迁移规则格式；可选组件组合的兼容证据规则；旧现场记录迁移与漂移分类；组件备份能力的机器可读格式；各跨度的一致性窗口及资源预算；每个适配器已覆盖与未覆盖的数据；集群锁的 fencing 实现；凭据/CA 导出的接入方式；独立扩容能力的验收与基线提交协议。阶段 1 须为这些事项分配负责人及验收条目，未决项所影响的跨度保持不可发布。
